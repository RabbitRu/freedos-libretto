# Повторное ревью ядра FreeDOS для Libretto

12 ноября 2026. Исходная точка: `87e7c3a1dfdd03035008c811f76633f1160a8f4e`.

Это статическое ревью основных путей ядра: входа в DOS, загрузки программ,
памяти, часов, символьного ввода-вывода, IRQ-стеков и дисковых служб.
Дополнительно проверены сохранённые карты компиляторного эксперимента.
Это не построчный аудит всего дерева. Новые DOS-прогоны, нативные замеры
скорости и проверки совместимости в рамках этого ревью не выполнялись.
Код ядра и настройки выпуска не изменены.

## Найденные проблемы

### P1: сравнение флагов компилятора затронуло ёмкость кэша

В тестовых образах задано `BUFFERS=20`, но положительное число при
`DOS=HIGH` означает минимум: ядро заполняет буферами оставшуюся HMA.
Рост резидентного кода уменьшает число буферов. Одинаковое значение в
CONFIG.SYS поэтому не гарантирует одинаковый кэш.

Источники: [настройка образов](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/scripts/libretto/images.py#L34-L47),
[выделение буферов](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/kernel/config.c#L2153-L2194),
[перенос в HMA](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/kernel/inithma.c#L310-L347).

По четырём картам **486-артефакта** компиляторного эксперимента:

| Настройка | Конец HMA-кода | Первый свободный адрес | Расчётное число буферов |
| --- | ---: | ---: | ---: |
| `size` | `a9b0` | `a9c0` | 41 |
| `scheduled-size` | `ab30` | `ab40` | 40 |
| `scheduled` | `aa40` | `aa50` | 41 |
| `hot-speed` | `afa0` | `afb0` | 38 |

Это расчёт по картам и формуле `(0xfff0 - HMAFree) / 532`, а не чтение
`LoL->nbuffers` из работающей системы. Происхождение данных и арифметика:
[compiler-cache-capacity.json](measurements/2026-11-12/kernel-review/compiler-cache-capacity.json).

Прежние измерения остаются результатами целых конфигураций, однако разницу
нельзя полностью приписывать генерации кода. В частности, `scheduled`
имеет те же 41 буфер и тоже проиграл по числу инструкций: ёмкость кэша
не объясняет все результаты. Оснований менять принятый `-os` пока нет.

Следующий контрольный эксперимент должен использовать одинаковое точное
число буферов, например `BUFFERS=-20`, и сохранять фактические `nbuffers`,
`bufloc`, размер HMA-кода и свободную conventional memory. Нужны оба вида
сравнения: фиксированная ёмкость для оценки кода и штатная конфигурация
для оценки суммарного результата. Это относится и к диагностическим
сборкам: счётчики увеличивают код и могут менять доступную HMA.

### P2: повторный рост JFT оставляет предыдущие таблицы в памяти

В [SetJFTSize](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/kernel/newstuff.c#L32-L64)
увеличение числа файловых дескрипторов выделяет новый блок и заменяет
указатель PSP, не освобождая предыдущую внешнюю таблицу. В исходнике
это уже отмечено TODO. Блоки сохраняются до очистки памяти процесса.

Например, увеличение 20 → 40 → 80 → 160 оставляет предыдущие внешние
таблицы: 48 + 80 байт с округлением до параграфа и два MCB по 16 байт,
всего 160 байт DOS-памяти сверх последней необходимой таблицы. На обычном
низком размещении это conventional memory. Экономия зависит от поведения
программы; обычный запуск с 20 дескрипторами выигрыша не даст.

Исправлять следует с учётом владения таблицей: нельзя без проверки
освобождать произвольный указатель из PSP. Проверки: повторный рост,
уменьшение и новый рост, сохранность открытых/дублированных дескрипторов,
наследование через EXEC, отказ выделения и завершение процесса. Верхние
границы размера также требуют отдельной проверки 16-битной арифметики.

### P2: одиннадцатая INSTALL выходит за границу массива

В [_CmdInstall](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/kernel/config.c#L2591-L2627)
массив содержит 10 элементов. Условие `numInstallCmds > LENGTH(...)`
пропускает значение 10, после чего записывается элемент с индексом 10.
Это подтверждённая по исходнику ошибка границы, возможная при суммарно
11 командах `INSTALL`/`INSTALLHIGH`. Конкретное повреждение соседних
данных и его последствия в DOS не воспроизводились.

Кандидат на отдельное исправление: проверка `>=` и сценарии с 9, 10,
11 командами, включая смешанные INSTALL/INSTALLHIGH. Это исправление
корректности загрузки, а не оптимизация скорости.

## Направления оптимизации вне FAT32

| Направление | Предлагаемое изменение | Где возможна польза | Приоритет / риск |
| --- | --- | --- | --- |
| Загрузка EXE | Читать релокации небольшими пакетами | Запуск EXE и загрузка оверлеев | Высокий / средний |
| Часы и дата DOS | Повторно использовать результат преобразования тика; сократить проход по годам | Частые AH=2Ch/2Ah, получение файловых времён | Высокий / средний |
| Управление памятью | Устранить потерю JFT; исследовать повторные проходы MCB в EXEC | Свободная DOS-память, запуск программ | Высокий для JFT; средний для ускорения / средний |
| Обработка INT 21h | Узкие быстрые пути по профилю реальных вызовов | Программы, часто обращающиеся к DOS | Средний / высокий |
| IRQ-стеки и размещение данных | Проверить минимальный профиль и фактическое размещение в UMB | Доступная память; иногда стоимость цепочки IRQ | Средний / высокий |
| Консоль | Убрать повторный поиск SFT, группировать подходящие записи | Оболочка, установщики, текстовый интерфейс | Низкий для игр / средний–высокий |
| Ожидание CPU | Проверить существующий IDLEHALT на Libretto | Потребление и нагрев при ожидании | Отдельный эксперимент / средний |

### Загрузчик EXE: конкретный небольшой эксперимент

[DosExeLoader](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/kernel/task.c#L759-L805)
уже читает тело программы блоками до 32 256 байт. Однако таблица
релокаций читается отдельным `DosRWSft` на каждую 4-байтовую запись.
Пакеты по 16 записей уменьшат число этих внутренних вызовов с N до
`ceil(N/16)`. Это не обещание такого же уменьшения физических чтений:
существующий секторный кэш уже может их обслуживать.

Буфер на 64 байта требует проверки максимального использования стека:
внутренние стеки дисковых/символьных функций имеют по 384 байта.
Не следует сразу помещать туда секторный буфер. Сохранять порядок
релокаций, включая повторные адреса; проверить границы пакета и сектора,
таблицы больше 64 КиБ, короткое чтение, OVERLAY/LOADONLY, COM и ошибки
освобождения памяти. Измерять время EXEC, число внутренних чтений,
BIOS-запросы, размер кода и память. В установившемся игровом цикле без
загрузки оверлеев эффекта не ожидается.

### Часы: избегать одинаковых вычислений внутри одного тика

[clk_driver](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/kernel/sysclk.c#L61-L101)
при каждом чтении повторяет преобразования с длинными делениями.
[DosGetDate](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/kernel/systime.c#L114-L152)
затем каждый раз идёт по годам от 1980-го — для 2026 года это 46 шагов.

Кандидаты: кэшировать hh:mm:ss:cc по последнему BIOS-тику во встроенном
драйвере; для даты кэшировать преобразование по номеру дня либо ускорить
арифметику календаря без дополнительной памяти. BIOS-чтение сохранять
на каждом запросе: оно учитывает переход суток и внешние обработчики.
Кэш не должен подменять установленный пользователем драйвер CLOCK$.

Проверки: совпадение результатов на всех тиках суток, переход полуночи,
установка времени/даты, високосные годы и календарные границы, BIOS-хуки
и замена драйвера часов. Сначала измерить долю этих служб в выбранных
программах. Игра, читающая PIT или BIOS напрямую, этот код не вызывает.

### INT 21h: сначала профиль, затем отдельные службы

[entry.asm](https://github.com/RabbitRu/freedos-libretto/blob/87e7c3a1dfdd03035008c811f76633f1160a8f4e/kernel/entry.asm#L243-L449)
уже содержит быстрые пути для AH=25h/35h и обработку части запросов на
пользовательском стеке. Общий обработчик в `inthndlr.c` копирует
регистры в локальную структуру и обратно; некоторые простые запросы
могут обходиться меньшей работой.

Нужна гистограмма AH и доля времени внутри ядра на реальных программах.
После этого выбирать одну частую службу. Общие действия InDOS,
PSP/стеков, Ctrl-Break, сетевых и TSR-хуков, флагов и сохранения регистров
нельзя удалять как ненужные. Защищённый режим и DPMI-переходы требуют
проверок с конкретным внешним DOS-extender/менеджером.

### Память, IRQ и консоль: полезно, но с ограничениями

- `DosMemLargest` уже использует поиск посредством заведомо неуспешного
  запроса размера FFFFh; лишнего выделения и освобождения здесь нет.
  EXEC может затем повторно пройти цепочку при реальном выделении.
  Объединять поиск можно только с сохранением first/best/last-fit и UMB-
  поведения. Постоянный кэш MCB рискован: программы обращаются к цепочке.
- `STACKS=9,256` означает 2304 байта дополнительных IRQ-стеков без учёта
  накладных расходов. Их размещение в UMB уже поддержано. `STACKS=0`
  экономит эту область и пропускает установку обёрток, но требует тестов
  вложенных IRQ, маленького стека приложения, TSR, мыши, таймера и звука.
  Не все игровые IRQ проходят через эти обёртки. Это вариант профиля,
  а не безопасная универсальная смена значения по умолчанию.
- Вывод AH=09h обрабатывается посимвольно; `write_char_stdout` повторяет
  поиск SFT. Сокращение поисков и пакетирование перенаправленного вывода
  заслуживают отдельного теста. Прямой вывод в VRAM может обходить ANSI,
  INT 29h, BIOS и альтернативные устройства, поэтому требует явного режима.
- `HLT` и IDLEHALT уже реализованы. Их проверка полезна для батареи и нагрева,
  но не ускоряет рендеринг и может менять поведение циклов опроса.

## Что не стоит обещать

Обычно DOS-игра сама управляет видеорежимом, рисованием и звуковым
оборудованием либо пользуется собственными библиотеками и внешними
службами. Оптимизация ядра не заменит memcpy внутри игрового EXE,
рендерер, микшер, VBE BIOS, HIMEM/JEMM или DPMI-хост. Их ревью — отдельный
объект работы. Если ядро занимает лишь 1% времени кадра, даже устранение
всей этой работы даст около 1% прироста FPS, а не десятки процентов.

MMX в ядре и глобальный `-ot` сейчас имеют низкий приоритет: нужны
сохранение состояния x87/MMX, доказанная горячая нагрузка и место в
16-битном сегменте. Расширение/разбиение сегментов — архитектурная работа,
которая сама по себе не гарантирует ускорения.

## Предлагаемый порядок

1. Зафиксировать ёмкость кэша в сравнительных экспериментах и добавить
   измерение реального числа буферов; затем повторить нужные сравнения.
2. Отдельными исправлениями закрыть границу INSTALL и владение JFT.
3. Первым экспериментом ускорения вне ФС взять пакетное чтение релокаций
   EXE; затем часы/дату с проверкой эквивалентности.
4. Снять профиль DOS-вызовов выбранных игр и только после этого менять
   вход в INT 21h, MCB или конфигурацию IRQ-стеков.

Для каждого кандидата нужны отдельные данные о числе инструкций, реальном
времени, размере кода и расходе памяти. В этом ревью предполагаемая польза
оценена качественно; измеренные проценты ускорения новым кандидатам
не приписываются.
